# Part 1. 왜 하네스 엔지니어링인가?

> AI 코딩 도구를 쓰는데 결과가 들쭉날쭉하다면, 모델을 바꿀 게 아니라 **하네스**를 바꿔야 합니다.

## 하네스가 뭔데?

말(horse)에게 씌우는 고삐를 영어로 harness라고 합니다.

AI 코딩에서 하네스는 **AI를 감싸는 시스템** 전체를 의미합니다. 프롬프트, 도구 설정, 자동 검사 스크립트 — 이 모든 게 하네스입니다.

```
[하네스 없이]
개발자: "로그인 기능 만들어줘"
AI: (코드 작성) → 테스트 안 함 → 보안 취약점 → 배포 후 사고

[하네스 있을 때]
개발자: "로그인 기능 만들어줘"
AI: (코드 작성) → 자동 포맷팅 → 자동 보안 검사 → 자동 코드 리뷰 → 테스트 통과 확인 → 완료
```

차이가 보이시나요? **모델은 같습니다.** 감싸는 시스템만 달라졌을 뿐입니다.

## 실제 성과

LangChain 팀은 2026년에 이런 실험을 했습니다:

- **같은 모델**(Claude)로 Terminal Bench 2.0 벤치마크를 돌림
- 하네스만 개선: **52.8% → 66.5%** (+13.7점)
- Top 30에서 **Top 5**로 상승

모델을 바꾸지 않고, 모델을 감싸는 시스템만 바꿨을 뿐입니다.

## 하네스의 3축

하네스를 바꿀 수 있는 지점은 딱 3가지입니다:

### 1. System Prompt (규칙서)

AI에게 주는 행동 매뉴얼입니다.

```
예시:
- "코드를 쓰기 전에 반드시 계획을 설명해"
- "함수는 50줄 이내로 써"
- "테스트 먼저 쓰고, 절대 테스트를 약하게 바꿔서 통과시키지 마"
```

회사에 새로 입사한 사람에게 "우리 팀은 이렇게 일해"라고 알려주는 온보딩 문서와 같습니다.

### 2. Tools (도구)

AI가 사용할 수 있는 도구를 선택하고 구성합니다.

```
예시:
- 코드 리뷰 에이전트: 코드 쓰고 나면 자동 검사
- 보안 리뷰 에이전트: 인증/API 코드에 자동 투입
- 빌드 에러 해결사: 빌드 실패하면 즉시 분석
```

혼자 다 하는 게 아니라, **전문가 팀을 구성**해주는 겁니다.

### 3. Middleware (자동 검사)

모델 호출과 도구 호출을 감싸는 훅(hook)입니다.

```
예시:
- 파일 수정할 때마다 자동 포맷팅
- rm -rf 같은 위험한 명령은 자동 차단
- API 키가 코드에 들어가면 자동 경고
- 같은 파일을 4번 이상 수정하면 "잠깐, 다시 생각해봐" 경고
```

공장의 **품질 검사 라인**과 같습니다. 사람이 매번 체크하는 게 아니라, 시스템이 자동으로 합니다.

## 하네스 설계 원칙

### DO (해야 할 것)
- **단순하게 시작한다** — 훅 1~2개부터
- **모델이 계획을 세우게 한다** — 하네스가 계획하지 않는다
- **가드레일, 재시도, 검증을 구현한다**
- **Rippable하게 만든다** — AI가 똑똑해지면 제거할 수 있는 로직만 넣는다

### DON'T (하지 말 것)
- 거대한 제어 흐름을 만들지 않는다
- 하드코딩된 파이프라인을 만들지 않는다
- 벤치마크 점수만 보지 않는다

## Claude Code에서의 하네스

Claude Code에서 하네스는 이렇게 매핑됩니다:

| 하네스 축 | Claude Code 구현 |
|----------|----------------|
| System Prompt | `CLAUDE.md` + `rules/*.md` |
| Tools | 커스텀 에이전트 (code-reviewer, security-reviewer 등) |
| Middleware | `hooks/` 스크립트 (settings.json에 등록) |

다음 편에서는 첫 번째 축인 **System Prompt (CLAUDE.md + rules)**를 실전으로 파헤칩니다.
