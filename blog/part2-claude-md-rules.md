# Part 2. CLAUDE.md — AI에게 주는 업무 매뉴얼

> 회사에 새로 들어온 사람에게 "우리 팀은 이렇게 일해"라고 알려주듯, AI에게도 매뉴얼이 필요합니다.

## CLAUDE.md가 뭔데?

Claude Code는 세션을 시작할 때마다 **기억이 리셋**됩니다. 어제 "함수는 50줄 이내로 써"라고 말했어도, 오늘은 모릅니다.

`CLAUDE.md`는 매 세션 시작 시 Claude가 자동으로 읽는 파일입니다. 여기에 적힌 규칙은 **항상** 적용됩니다.

```
[CLAUDE.md 없이]
세션 1: "테스트 먼저 써" → OK
세션 2: (까먹음) → 테스트 없이 코드부터 작성
세션 3: "아 또... 테스트 먼저 쓰라고" → OK
세션 4: (또 까먹음)

[CLAUDE.md 있을 때]
세션 1~무한: 항상 테스트 먼저 작성 (규칙에 적혀있으니까)
```

## 규칙 파일 구조

하나의 거대한 CLAUDE.md에 다 넣으면 AI가 랜덤하게 무시합니다. **150~200개 명령이 한계**입니다.

우리는 주제별로 분리합니다:

```
~/.claude/My_ClaudeCode_Skill/rules/
├── workflow.md          # 일하는 방식
├── coding-style.md      # 코드 품질 기준
├── testing.md           # 테스트 규칙
├── security.md          # 보안 체크리스트
├── git-workflow.md      # Git 컨벤션
├── context-management.md # 세션 관리
├── agents.md            # 에이전트 목록
├── hooks.md             # 훅 문서
└── harness-engineering.md # 하네스 원칙
```

## 핵심 규칙 해설 (실전 예제)

### 1. workflow.md — "코드부터 쓰지 마"

가장 흔한 AI 실패: 질문하자마자 코드부터 씀 → 방향이 틀림 → 다시 작성 → 시간 낭비

```markdown
# 우리 규칙
1. Explain: 문제 분석 + 접근법 2개 이상 제시 (코드 없이)
2. Approve: 사용자가 "ㅇㅇ" 하면 진행
3. Execute: 그때 코드 작성
4. Reflect: 핵심 결정 1~2문장 요약
```

**비유**: 건축가가 도면 없이 벽돌부터 쌓지 않듯, AI도 설계 먼저.

**실제 대화 예시**:
```
사용자: "로그인 기능 만들어줘"

[규칙 없을 때]
AI: "네, 로그인 기능을 만들겠습니다." → 바로 코드 500줄 작성

[규칙 있을 때]
AI: "로그인 기능에 두 가지 접근법이 있습니다:
     Option A: JWT 토큰 방식 — 장점: 확장성, 단점: 토큰 관리
     Option B: 세션 방식 — 장점: 단순, 단점: 서버 부하
     어떤 방식으로 갈까요?"
사용자: "A로"
AI: (그제서야 코드 작성)
```

### 2. coding-style.md — "깨끗하게 써"

```markdown
# 제한 기준
| 항목 | 기준 |
|------|------|
| 함수 길이 | < 50줄 |
| 파일 길이 | < 400줄 |
| 중첩 깊이 | < 4단계 |
| 테스트 커버리지 | > 80% |
```

**왜 이게 필요한가?** AI는 제한이 없으면 200줄짜리 함수를 아무렇지 않게 작성합니다. 사람이 읽을 수 없는 코드가 나옵니다.

### 3. testing.md — "테스트를 약하게 바꾸지 마"

```markdown
# 금지 패턴 (구현을 고쳐, 테스트를 고치지 마)
- toBeTruthy()로 구체적 매처를 대체하는 행위
- test.skip으로 실패하는 테스트를 건너뛰는 행위
- 타임아웃을 30초 이상으로 늘리는 행위
- assertion을 삭제해서 테스트를 통과시키는 행위
```

**비유**: 시험 문제가 어려우면 답을 공부하지, 문제를 쉽게 바꾸지 않는 것과 같습니다.

**실제 상황**:
```
[규칙 없을 때]
AI: 테스트 실패 → "테스트를 수정하겠습니다" → expect(result).toBeTruthy() 로 변경 → 통과!
(하지만 실제 버그는 그대로)

[규칙 있을 때]
AI: 테스트 실패 → "구현 코드에 버그가 있습니다" → 실제 로직 수정 → 원래 테스트 통과!
```

### 4. security.md — "보안 사고 나면 끝이야"

```markdown
# Pre-Commit 체크리스트
- [ ] 하드코딩된 시크릿 없음 (env vars 사용)
- [ ] 모든 사용자 입력 검증/살균
- [ ] SQL: 파라미터 쿼리만 사용
- [ ] XSS: HTML 출력 살균
- [ ] 에러 메시지에 내부 정보 노출 안 함
```

### 5. context-management.md — "메모리 관리"

Claude Code는 대화가 길어지면 앞부분을 잊습니다.

```markdown
# 규칙
- 70% 컨텍스트 사용 → /compact 실행
- 80% 넘기지 말고 새 세션 시작
- /clear 전에 반드시 세션 학습 정리
```

**비유**: 책상이 가득 차면 정리하고, 서류는 파일 캐비닛에 넣는 것과 같습니다.

## 핵심 팁: WHY를 같이 써라

```markdown
# 나쁜 예
- TypeScript strict mode 사용

# 좋은 예
- TypeScript strict mode 사용 — implicit any 타입으로 프로덕션 버그가 발생한 적이 있음
```

WHY가 있으면 AI가 **예외 상황에서도 올바른 판단**을 합니다. WHY 없이 규칙만 있으면, 상황에 맞지 않아도 기계적으로 따릅니다.

## CLAUDE.md vs 훅, 언제 뭘 쓰나?

| 상황 | CLAUDE.md | 훅 |
|------|----------|-----|
| 100% 매번 실행돼야 하는 것 | | O |
| 판단이 필요한 가이드라인 | O | |
| 코드 포맷팅 | | O (prettier) |
| "함수 50줄 이내" | O | |
| API 키 감지 | | O (secret-detector) |
| "테스트 먼저 써" | O | |

**원칙**: 자동화할 수 있으면 훅, 판단이 필요하면 CLAUDE.md

다음 편에서는 두 번째 축인 **훅(Hooks)**을 실전으로 파헤칩니다.
